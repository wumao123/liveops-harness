# 主播运营 Agent：项目与面试速记

更新：2026-10-19。先看项目和例子，再读问答。数字来自已有实验，本次仅整理文档。

## 一、先把项目说清楚

### 30秒介绍

> 我做了一个主播运营助理：播前准备商品手卡，播中回答商品问题、协助切品和申请发券，播后复盘。模型负责理解和写作，程序负责查商品、检查权限、等待审批和保存进度。多款手卡可以并行生成，一款失败不用全部重做。项目重点是多轮不认错商品、不用旧库存、操作不重复。

目前是**五款商品的本地仿真，接了真实DeepSeek模型，没有接淘宝生产接口。**

### 为什么要做 Harness？

Harness可以理解成**模型外面的一套执行管理程序**。模型能提出“发券”，但程序还要确定：给谁发、发多少、用户是否授权、是否需要审批、失败能否重试。

项目主要用这些技术：

| 技术 | 在项目里干什么 |
|---|---|
| Python + FastAPI | 提供后端接口 |
| DeepSeek + HTTPX | 理解口语、生成建议和手卡 |
| LangGraph | 串联指令流程，暂停等待审批，再恢复 |
| 线程池 | 同时准备不同商品的材料 |
| SQLite | 保存商品、偏好、对话状态、任务和用量；审批进度另存SQLite |
| HTML/CSS/JavaScript | 展示聊天、审批和备播工作台 |

## 二、用一场直播把模块串起来

下面是讲解例子，实际推荐顺序以页面展示为准。

1. **主播说：“记住，口播简短，不夸大功效。”** 系统把明确偏好存起来，之后生成材料时读取。
2. **“推荐三款商品。”“给第二款写口播。”** 系统保存推荐顺序，从列表找到第二款，再查最新商品资料。聊天超过四轮，列表也能保留。
3. **“准备这三款的手卡并审核。”** 创建任务：选品→三路手卡→三路审核→汇总。默认最多三个任务同时运行。
4. **其中一款售罄，要换商品。** 用户确认后，只重做受影响的材料；其他商品资料和偏好没变，就复用原结果。
5. **“给面霜发10元券。”** 缺张数就追问。提交完整指令后，等待用户审批；确认时再查库存、版本和当前阶段。
6. **券可能发出了，但接口没返回。** 先查回执，不能直接重发。播后按实际提交记录复盘。

把流程记成一句话：**听懂需求→查最新事实→分工完成→检查结果→保存状态；涉及改价发券，先审批。**

## 三、高频面试题

### 1. 意图识别怎么做，为什么这么做？

**让模型把一句话变成固定格式，再由代码检查。** 例如：

```json
{"type":"issue_coupon","sku":"SK-102","amount_cents":1000,"quantity":20}
```

意思是：给SK-102发20张10元券。金额用整数“分”保存。

程序继续检查商品是否存在、金额张数是否来自用户原话、是否需要审批。版本信息由程序读取，不让模型猜。

配置模型后，先用模型理解；临时错误或坏JSON经过有限尝试仍失败，可退回规则。未配模型时直接用规则。

**选型理由：模型能理解更多口语，规则和代码能守住明确约束。** 没有训练专门的意图分类器。

### 2. “它”“第二款”怎么认？缺参数怎么办？

记住三个对应关系：

- **第二款：**查当前阶段保存的推荐列表。
- **它：**查最近讨论的商品；刚比较多款、对象不明确时先问。
- **上一款：**查业务库保存的上一个讲解商品。

缺金额、张数就追问；“如果明天发券呢”属于讨论，不能当立即执行。代码会对照原话，防止模型默认补“一张”。

目前还不能保证用户下一轮只说“20张”，就自动补齐上一条操作；稳妥用法是补充完整指令。

### 3. 多Agent和子Agent到底怎么设计？

**按工作分角色，再按商品拆任务。**

- 选品：确定准备哪些商品。
- 写手：生成单款商品手卡。
- 审核：核对该商品的数字、卖点、来源和版本。
- 汇总：收集合格材料，列出未通过的商品。

当前只有写手角色可独立调用模型，其余主要由代码完成。角色只获得需要的资料和只读能力，不能自行发券，也不能无限创建子Agent。

**为什么拆？方便独立商品并行、资料隔离和失败恢复。** 简单单商品任务用一个Agent或模板也可以；尚未证明多Agent的回答质量更高。

### 4. DAG是什么？任务怎么并发？

**DAG就是一张“谁要等谁”的任务图。** 三款商品共8个任务：

```text
选品
 ├─ A手卡 → A审核 ─┐
 ├─ B手卡 → B审核 ─┼─ 汇总
 └─ C手卡 → C审核 ─┘
```

代码先检查依赖有没有循环、审核有没有拿错商品。然后找出前置任务已完成的任务，用 `ThreadPoolExecutor` 线程池运行，默认最多3个。

当前按批次推进：这一批结束，再安排下一批。模型请求主要在等网络，把等待重叠起来就能省时间；不是让CPU计算变快。

### 5. 一款失败或售罄，为什么不用全部重做？

**失败重试和商品变化分开处理。**

网络暂时失败：保存成功分支，有限重试失败任务。每个任务都有ID、状态、尝试次数和结果，状态与结果一起存库。

商品售罄：用户确认替换后，重新选品，重做替换商品的手卡和审核，再汇总。其他商品及偏好没变，原材料继续用。偏好变了，受影响的写手也要重做。

这叫**局部重规划**。它省重复调用，代价是要维护商品版本、偏好和任务依赖。

### 6. 上下文放什么？长度多少？

**上下文就是这次递给模型的材料，按当前任务组装。**

对话请求拿当前阶段、讨论商品、推荐列表、近期对话和最新商品事实。写手只拿本商品、偏好和必要的上游结果；审核拿本商品与对应草稿。

主要上限：

- 当前阶段的对话状态包：默认 **4000字符**。
- 近期对话：最多 **4轮**；每轮用户最多200字符、回答240字符，超预算继续移除最旧轮。
- 子任务材料：最多 **16000字符**，超限要求缩小任务。
- 完整回答：另存数据库，需要时回查。

**4000字符只限制这个状态包。** 整次请求还会加入提示词和商品资料；它不是模型的总token窗口。

### 7. 只有四轮，怎么长期跟住主播思路？

**聊天原话可以裁掉，仍有用的状态单独保存。**

例如第一轮推荐A、B、C，即使这段话退出四轮窗口，推荐列表还在。之后问“第二款”，仍可找到B。播前、播中、播后分别保存讨论状态，价格库存另查实时库。

做过一个真实模型开发检查：推荐后插入8轮离线状态查询，再问第二款，仍正确定位。这验证了这个场景，不代表所有长对话都可靠。

当前主要记住商品焦点和顺序，不能保证记住主播几小时内所有理由、限制和未完成目标。继续扩展时，先增加“当前目标、已确认限制、待解决问题”，再考虑摘要或向量检索。

### 8. 记忆分几层，为什么？

**分三类，因为它们的来源和更新方式不同。**

| 类别 | 例子 | 处理方式 |
|---|---|---|
| 声明偏好 | “口播简短” | 用户明确说记住才保存 |
| 业务事实 | 当前款、价格、库存 | 查业务库，旧聊天不能覆盖 |
| 已提交行为 | “确实发过20张券” | 查操作记录，保留证据 |

不能都写成摘要：偏好可以长期用，库存随时变，发券是否成功要看实际提交结果。

偏好目前是一个最多120字符的字段，按直播间保存，可删除、重启后可读；还不是跨场次的完整主播画像。行为与偏好不同，只提示用户确认，不自动改写偏好。

三个词这样区分：**记忆是以后还能用的信息；上下文是这次给模型看的材料；Checkpoint是任务暂停的位置。**

### 9. 持久化为什么选SQLite，不用Redis或向量库？

**现在数据少、字段明确，SQLite部署简单，还能用事务保证一组修改一起成功或一起撤销。**

业务、偏好、对话状态、任务结果和预算都落库；审批进度由LangGraph保存到独立SQLite库。服务重启后可以继续读取。

Redis适合后续缓存和限流，向量库适合大量文字的语义检索。目前按商品ID、任务ID直接查询就够，额外加组件不能解决库存真假或重复发券。

生产扩展会考虑PostgreSQL承接业务和任务数据，Redis辅助限流，再做多租户隔离和容量测试。当前没有部署这套生产架构。

### 10. 高并发怎么处理？

**先分清“一个计划内并行”与“很多用户同时请求”。**

计划内默认3线程。不同命令可以并行，同一命令ID在进程内加锁；提交时再用数据库事务、唯一键和版本检查防止重复或覆盖。重复请求返回已有结果、不再执行一次，这叫幂等。

同一准备计划还会在数据库登记“谁正在执行、有效到何时”，这叫租约。过期或失去执行权，就不能继续保存结果。

本机离线测试中，1/4/8线程的吞吐约212/325/316次每秒，说明线程更多未必更快。**这是直接调用离线程序的结果，没有经过HTTP网络或真实模型，不能当线上QPS。**

生产还要补：入口排队、全局和租户级并发限制、每分钟请求/token限流，再做真实链路压测。

### 11. 用了Function Calling吗？工具有哪些？

**当前主播项目是模型输出JSON动作，Python按动作执行，没有使用原生 `tool_calls` 循环。**

主链能查状态、推荐、写口播、复盘、建准备计划、存偏好，以及受控切品、改价、发券。准备链只开放选品、写手、审核、汇总对应的只读能力。

模型请求和工具执行要分开数：一次推荐可能请求模型理解一次、组织回答一次，中间还有本地查库。

每条指令只接受一个受限动作，当前JSON方案够用。即使换成原生Function Calling，参数检查、审批和防重复提交仍要自己做。

### 12. 调用失败怎么办？如何限制成本？

**按错误处理，不统一重试。**

- 超时、429、5xx：有限重试；意图理解失败可退回规则。
- 坏JSON：有限修正；缺参数问用户，鉴权错误不盲目重试。
- 商品或偏好变了：读取新状态，确认后重规划。
- 发券结果未知：查原操作回执；连续三次查询仍未确认，转人工处理。

默认预算如下，重启或恢复不会清零：

| 范围 | 默认限制 |
|---|---|
| 一条指令 | 6次模型请求、10万预估token |
| 一个准备计划 | 20次模型请求、30万预估token；总任务执行24步 |
| 同一直播间累计 | 200次模型请求、200万预估token，不自动补充 |
| 任务恢复 | 同一任务默认最多2次执行尝试；同计划最多2次重规划 |

请求前先在数据库扣住预计额度，拿到模型返回的用量后再核对；失败或用量未知也留记录。每个写手线程都绑定同一个计划预算，防止并行时各花各的。

注意：任务内部还有有限请求重试，所以“任务最多两次尝试”不等于“总共两次HTTP请求”。预估token不是精确费用，这些默认值也没有证明最优；长场次还需要补额、告警和限流。

时间方面，单次计划推进在30秒边界检查，已发出的请求仍受自身超时限制；审批默认5分钟有效。

### 13. 为什么评估这些指标？不同方法对比过吗？

**指标要对应业务问题：听没听对、内容有没有错、等多久、花多少、失败后有没有重复执行。**

意图按“动作、商品、关键参数全部正确”计分，正确题数除以总题数。审核既看错误稿漏过多少，也看正常稿误拒多少。速度看中位数和P95——后者关注慢的那部分请求。成本统计全部请求和已知token，包括失败；恢复统计重做任务和调用数。

实际做过这些对照：

| 比较什么 | 实测结果 | 怎么理解 |
|---|---|---|
| 规则 vs 真实模型理解 | 同24条开发题：19/24 vs 20/24 | 普通16题规则全对、模型14题；挑战8题规则3题、模型6题，各有长短 |
| 串行 vs 3线程 | 同DAG、真实模型，各5次；耗时中位2.995→1.070秒 | 独立商品能重叠等待，不能说明回答更准确 |
| 全量上下文 vs 按角色裁剪 | 本地40个任务包，字符量减少88.9% | 材料更少，不等于费用也降88.9% |
| 全量重跑 vs 局部恢复 | 本地临时失败实验各10次，任务尝试140→90 | 少做重复任务，没有调用真实模型 |
| 全量换品重建 vs 局部重规划 | 一个真实模型场景，恢复请求3→1、任务8→4 | 耗时1.166与1.140秒接近，主要收益是少调用 |
| 关闭 vs 开启审核 | 45个预设错误稿从全部放行变成全部拦住，5个正常稿通过 | 验证这组错误能拦住，不代表自然模型永不出错 |

**尚未做完整的单Agent与多Agent质量对照，也没有长期记忆总体准确率。** 下一步应固定模型、工具、题目和总预算，用新题同时比较质量、安全、耗时和全部调用量。

面板指标也别混用：`ok_rate`只是流程状态统计；采纳率只统计有明确反馈的建议。两者都不是成交提升，目前没有GMV结果。

### 14. 讲一个真正的难点，怎么讲？

选一个故事，按**发生什么→为什么→怎么改→如何验证**讲。

**故事A：模型补了一张券。** 用户没说张数，模型却填了1。原因是字段合法不代表用户授权。改为对照原话，缺数量就问；条件句只讨论。旧实验保留了这个错误，新逻辑有回归检查。

**故事B：聊天裁掉了，第二款不能认错。** 只留四轮会丢早期顺序，全留又越来越长。把推荐顺序单独保存，完整回答另存。插入8轮离线查询后，再用真实模型追问，正确定位第二款。

**故事C：切回播中，旧审批不能复活。** 只检查“现在是播中”会漏掉中间切过播后。改为记录阶段变化次数，审批绑定旧版本就失效。在线人数变化不影响这个版本，避免无关更新让审批失效；本地与远端路径都有回归检查。

这些是本地开发问题。现在还欠缺真实平台接入、多租户鉴权、完整语义审核和生产容量验证。
