# 主播运营 Agent Harness：一条业务主线讲清项目与面试题

核对日期：2026-10-19。依据当前 `liveops/` 源码与已保存的实验记录重写。本文讲的是 **LiveOps 主播项目**；论文 Agent 的 nano-cc、检索指标和 native tool calling 不属于本项目。

阅读顺序：项目简介约3分钟，完整例子约5分钟，高频问题约15–20分钟。第一遍先读每题的加粗结论，再看实现与数字。文中“下一步”均指尚未完整实现的方案；历史实验按当时源码口径保留，本次整理没有重新调用模型或重跑实验。

## 一、项目简介：为谁做，解决什么，用什么实现

### 1. 业务背景与需求

主播和运营在一场直播里会连续做三类事：播前选品、准备多款商品手卡；播中追问卖点、切品、申请改价和发券；播后按实际操作复盘。问题会穿插，例如刚推荐完三款，几轮后又问“给第二款写口播”，同时商品库存还在变化。

业务最需要解决的是四件事：**听懂当前意图；跟住讨论对象；使用最新商品事实；让有副作用的操作经过明确授权。** 多款材料还应能并行准备，一款失败或售罄时可以局部恢复。

当前项目使用五款护肤商品和本地业务库模拟这些流程，已经接入真实 DeepSeek 推理，但没有接入淘宝生产交易接口。没有真实用户运营数据、成交提升或GMV收益结论。

### 2. 一分钟项目介绍

> 我做了一个主播运营 Agent Harness，覆盖播前准备、播中建议和受控操作、播后复盘。DeepSeek 负责把口语变成结构化动作，以及根据商品事实组织建议；LangGraph 管理指令流程与人工审批。多商品准备采用有界 DAG，通过线程池并行生成各商品材料，按 SKU 隔离上下文，失败后恢复相关分支。SQLite 保存业务状态、偏好、上下文投影、任务材料和模型预算，Checkpoint 保存审批进度。我的重点是多轮不串对象、旧事实不当实时数据、建议不自动变成执行权限，并用真实模型小实验和工程回归验证这些机制。

### 3. 技术栈与选择理由

| 部分 | 当前实现 | 为什么这样选 |
|---|---|---|
| 后端/API | Python 3.11+、FastAPI、Uvicorn、Pydantic | 便于结构化入参校验、接口演示和测试 |
| 指令流程 | LangGraph `StateGraph`、`interrupt`、SQLite Checkpointer | 改价/发券需要持久化暂停，确认后恢复 |
| 模型接入 | HTTPX 调用兼容 Chat Completions 的接口；实测返回 `deepseek-flash` | 意图、建议、写手分别使用受限请求，统一记录预算与用量 |
| 多商品准备 | 自定义有界 DAG、`ThreadPoolExecutor`、结构化任务产物 | 商品依赖明确，便于并行、范围隔离和局部恢复 |
| 存储 | SQLite 业务库、WAL、事务、版本字段、唯一键；独立 Checkpoint 库 | 本地部署简单，可验证幂等和恢复；不声称已具备分布式容量 |
| 前端 | 原生 HTML/CSS/JavaScript 工作台 | 展示对话、审批、任务推进、来源、记忆和回执 |
| 验证 | pytest、真实模型开发集、受控机制实验、本地并发基线 | 分别验证契约、模型表现、设计取舍和容量趋势 |

本项目没有部署 Redis、向量数据库、Kafka、分布式 Agent 集群。后面提到这些组件时，都是按需求扩展的方案。

## 二、一场直播串起全部设计

记住这条总链：**用户表达 → 理解目标 → 组装必要材料 → 按依赖执行 → 校验结果 → 保存状态。**

```text
主播消息 + 当前阶段/商品快照/讨论状态
                   │
       LangGraph：load → interpret → gate
                   │
     ┌─────────────┼─────────────────┐
     │             │                 │
 只读建议       多商品准备          改价 / 发券
 查最新事实     创建有界DAG         interrupt等待确认
 生成并检查     工作台推进           Checkpoint落盘
     │        选品→并行手卡→审核→汇总    │
     │             │              重验版本、阶段和有效期
     │             │                 │
     └─────────────┴──────────────→ 事务提交 / 回执对账
                   │
          回答、审计、上下文投影与原文保存

所有模型请求另走：预算预留 → HTTP请求 → 按已知usage对账
```

下面是**连贯的业务示例**，不是一条已经完整跑过的实验轨迹；实际推荐顺序以当轮展示为准。

| 这场直播里发生什么 | 系统具体做什么 | 对应的设计点 |
|---|---|---|
| 播前说“记住：口播简短，不夸大功效” | 识别为显式偏好，写入 `preferences`，后续相关请求读取 | 可复用偏好有明确来源 |
| “推荐三款开场商品，说明顺序” | 代码限定候选，模型可在候选内组织建议；接纳后的顺序持久化为 `listed_skus` | 用户看到的顺序就是后续序号指代的依据 |
| 中间聊了几轮，再说“给第二款写口播” | 从当前阶段的结构化列表取第2个 SKU，再查该商品最新事实 | 早期推荐退出四轮窗口，列表仍能保留 |
| “它适合敏感肌吗” | 优先绑定讨论焦点；比较多款导致歧义时澄清。商品材料不支持的功效不能当作已证实事实 | 跟住对象与判断证据是两件事 |
| 明确准备 SK-101、102、103 的手卡与审核 | 聊天创建计划，工作台推进；1选品+3手卡+3审核+1汇总，共8任务 | 主流程接收目标，准备 Harness 管依赖和分工 |
| SK-101 售罄，操作者确认换成 SK-104 | 校验新商品与版本，重做选品、替换商品手卡/审核、汇总；其余有效分支复用 | 变化引发重规划，不当作网络失败重试 |
| 切到播中，说“给面霜发10元券” | 缺张数就追问，不能默认一张。随后提交完整的商品、金额、张数 | 模型识别出动作，不代表已获得完整授权 |
| 提交“给面霜发10元券20张” | 进入审批，Checkpoint 保存进度；确认后在提交前重验状态 | 人工审批与数据库校验各有职责 |
| 等审批时库存或阶段变了 | 旧提案可能被阻断，要求基于新状态重新发起 | 用户同意过，也不能执行过期提案 |
| 仿真平台已发券但响应丢失 | 标记 `unknown`，按原操作身份查询回执，确认后对账 | 结果未知不能当失败重新发券 |
| 播后复盘，评价建议是否采纳 | 读取已提交审计；反馈单独保存，采纳建议不触发交易 | 行为证据、用户反馈、执行授权分开 |

这就是各模块的联系：**意图确定做什么，DAG确定谁先谁后，上下文确定本步看什么，记忆保存以后需要什么，Harness约束能执行到哪里。**

## 三、高频问题：结合这个例子讲实现、取舍和证据

### 1. 意图识别怎么做？为什么这样做？

**主答：模型输出结构化候选动作，程序对照原话、业务状态和权限做校验。没有训练意图分类模型。**

`load` 先读业务快照与分阶段上下文；`_llm_action()` 以 temperature=0、JSON格式要求解析一个动作。动作可以是 `plan、brief、advise、prepare、clarify、switch_product、update_price、issue_coupon` 等；随后 `_guard_instruction()` 对照原始指令，`_normalize_action()` 检查类型、SKU、整数参数并补入程序读取的版本，最后经过 `policy.decide()` 风险门。

例如完整发券候选的核心是：

```json
{"type":"issue_coupon","sku":"SK-102","amount_cents":1000,"quantity":20}
```

金额以分为单位存整数；版本由程序读取，模型不能自己决定“当前版本”。未配模型时用规则；配置模型后模型优先，暂时性服务错误或坏结构经过有限尝试后可退回规则。**没有实现“规则命中就跳过模型”的通用快路径。**

为什么这样做？规则对明确命令稳定，模型更能覆盖口语，但也会填入用户没说的参数。JSON合法、字段正确、用户授权完整，必须分别检查。后面的业务校验对两种解析来源都生效。

真实开发对照里，同24题规则匹配19题、模型20题；普通16题规则全对，模型14题；挑战8题规则3题、模型6题。它支持“互有长短”，不支持“接模型全面更强”。

### 2. “它”“第二款”和缺参数怎么处理？能连续补槽吗？

**主答：序号查展示列表，代词查讨论焦点，上一款查业务状态；对象不清或写操作缺参数就澄清。**

当前阶段保存 `focus_sku、focus_ambiguous、listed_skus`。“第二款”绑定该阶段最后接纳的推荐列表，而不是数据库商品顺序。“讨论的商品”与“直播正在讲的商品”分开，`previous_sku` 由切品事务持久化。

同时比较多款后问“它”会触发歧义澄清；没有讨论焦点时，部分规则路径会回退当前商品，不能声称所有代词歧义都已解决。昵称、复杂否定和多目标指令也仍有覆盖边界。

发券缺张数会追问；条件、未来、否定语句，例如“如果明天给它发券呢”，按讨论处理，不能立即执行。金额和张数要与原话一致，不能靠模型补值。**当前缺参追问不等于完整跨轮自动填槽；不要承诺用户下轮只说“20张”就必然补齐旧提案。**稳妥路径是重新提交完整操作。

### 3. 项目真的有多 Agent / 子 Agent 吗？为什么拆？

**主答：有受控的多角色任务执行；主流程创建计划，商品准备 Harness 调度子任务。当前只有写手角色可独立调用模型，其他角色主要是确定性代码。**

| 角色 | 负责什么 | 看什么 / 能做什么 |
|---|---|---|
| 选品 `merchandiser` | 输出已经限定的准备商品范围 | 候选公开字段、相关偏好；只读 `catalog` |
| 写手 `copywriter` | 生成本商品结构化手卡 | 本 SKU、选品依赖；只读 `product`，可调用模型 |
| 审核 `compliance` | 核对SKU、价格、库存、卖点、来源和版本 | 本 SKU 与对应草稿；只读 `review` |
| 汇总 `director` | 组装合格材料，列出未通过商品 | 审核产物；只读 `assemble` |

角色不会自主递归创建更多 Agent，也没有任意 Bash、文件或改价权限。Skill 是角色允许使用的能力，Agent/角色任务是拿着目标和上下文完成一次工作，二者不是同一个概念。

拆分理由是商品分支独立、输入范围不同、审核契约不同、恢复范围不同。单商品、简单字段复制可以直接用一个流程或模板；这里没有证明多 Agent 的自然语言质量高于“单 Agent + 相同工具与护栏”。

### 4. DAG 并发具体怎么做？用线程还是异步？

**主答：Pydantic 校验任务依赖，自定义调度器找就绪任务，用 `ThreadPoolExecutor` 按波次执行，默认最多3个 worker。**

三商品的依赖如下：

```text
selection
  ├─ brief_0 → review_0 ─┐
  ├─ brief_1 → review_1 ─┼─ summary
  └─ brief_2 → review_2 ─┘
```

`PlanSpec` 拒绝循环、未知依赖、孤立节点和跨SKU审核。调度器选择 `pending` 且所有依赖 `succeeded` 的任务，先保存为 `running`，然后提交线程池。worker只返回本任务结果，主调度线程通过 `as_completed()` 收取，再把状态和材料一起持久化。

当前是**波次调度**：本波结束再选择下一波，不是某张手卡一完成就立即启动它的审核。默认三商品通常经历选品、三路手卡、三路审核、汇总四波。HTTP模型请求主要在等网络，线程可重叠等待；不把它解释为突破GIL、加速CPU计算。

默认并发3、内部可配置1–5，不是全服务只有3个请求，也不是生产租户级并发控制。真实写手对照中，相同DAG仅改变1/3 worker，各5次：完成中位耗时2.995秒→1.070秒，约2.80倍。双方调用总量没有因为并发而自动减少。

### 5. 子任务失败怎么办？与商品变化后的 replan 有何区别？

**主答：服务临时失败恢复原任务；商品或偏好改变则显式重规划，先判断旧结果还是否有效。**

任务有稳定ID、状态、累计尝试和材料ID。成功任务及产物在同一事务提交；可重试失败任务在明确恢复时重置为待运行，下游等依赖满足后继续。默认同一任务最多2次执行尝试。参数、权限、状态过期不能原样重试。

商品替换时，操作者提交 replacement 与期望计划版本；代码读取新事实，归档旧计划，重新计算失效范围。替换一款时重做 selection、该款 brief/review、summary；兄弟商品版本与偏好不变时复用其成功材料。偏好变了，相关写手分支也要失效。默认最多2次重规划，总任务步数和模型额度不清零。

真实单场景对照：三款准备后换一款，全量重建恢复阶段3次模型请求、8次任务执行；增量方案1次请求、4次执行，复用4个有效任务。耗时1.166秒与1.140秒接近，结论是减少重复工作，**没有证明显著提速**。

### 6. 上下文怎么设计？长度上限究竟是多少？

**主答：把“当前阶段的对话包”“实时商品事实”“角色任务包”分开组装，不向每次调用广播整场聊天。**

| 材料 | 当前边界 | 用途 |
|---|---|---|
| 当前阶段运行上下文包 | 默认4000字符，内部可设1600–8000 | 阶段、焦点、列表、统计、近期对话、原文ID |
| 近期对话 | 当前阶段最近4条轮次记录；每条用户最多200字符、回答最多240字符，再按包预算移除最旧轮次 | 保留局部表达和追问线索 |
| 意图候选商品 | 最多8款，优先命中商品、当前款、上一款，再补候选 | 解析商品对象；单字段另有裁剪 |
| 主播显式偏好 | 当前一个最多120字符的 `style` 字段 | 稳定表达要求 |
| 子任务上下文 | 序列化后最多16000字符，超限拒绝 | 当前角色、目标SKU、公开事实、直接依赖材料 |
| 完整回答与旧版计划 | 数据库存完整产物，提示中留片段/ID | 检查来源、人工回查与恢复 |

**4000字符只是运行上下文包预算，不是整次模型请求总长度，更不是模型窗口只有4000 token。** 意图请求还会加入商品字段和提示词。当前没有给所有模型请求统一的精确输入token窗口硬限制；输出另受各请求 `max_tokens` 限制，调用准入另受预算账本约束。

最新主路径使用 `Workspace.context()` 的回答240字符；旧 `recent_context()` 辅助逻辑里仍有400字符。面试回答当前主链上限时不要背旧值。

### 7. 只有四轮，能持续跟住主播的思路吗？

**主答：四轮保存近期措辞，结构化状态保存仍然有效的讨论对象和推荐顺序；完整原文外置。它支持已定义的工作流状态，不保证无限记住所有语义。**

`Workspace` 按播前/播中/播后维护独立话题投影。`reduce_state()` 接收事件，更新焦点、歧义标记、推荐列表和材料指针，再写入SQLite。即使推荐文本退出近期四轮，列表仍存在；切阶段也不会把播前推荐串成播中列表。价格库存始终重新查业务库。

实测过一个开发场景：真实模型先推荐三款，中间插入8轮离线状态查询，再让真实模型“给第二款写口播”；第一轮已退出四轮窗口，仍正确绑定最初展示的第二款，且没有跨阶段串列表。该检查共4次真实模型请求、4305个报告token；中间8轮不是模型对话，不能当作长期记忆总体准确率。

限制是：结构化投影仅保留已定义字段，没有把主播所有理由、临时约束和未完成目标都抽取出来；旧原文虽然可回查，也不是每次自动全量检索。因此不能保证几小时内任意暗示都正确。

下一步若支持长场次，应增加 `active_goal、已确认约束、待解决事项、指代所绑定的列表版本`，每次变更记录来源与适用阶段；再用更长、含纠正和话题切换的对话测试。先补缺失状态，再决定是否需要语义摘要或向量召回。

### 8. 记忆分几层？为什么这样分？

**主答：当前记忆视图分“显式声明、实时事实、已提交行为”三类来源；对话工作状态另外保存在 Workspace。分层按可信来源和更新方式划分。**

| 记忆视图 | 具体实现 | 更新与优先级 |
|---|---|---|
| L1 声明 | `preferences` 中主播明确要求“记住”的style | 新声明更新当前字段；可显式删除，不能覆盖业务红线 |
| L2 事实 | 业务表中的当前/上一商品、版本；价格库存按需查询 | 由业务事务更新，旧对话不能覆盖 |
| L3 行为 | 最近100条审计中筛选已提交操作，形成统计与事件引用 | 失败操作不当作已执行；行为不会自动变成偏好 |

为什么不全塞进一段摘要？三者的真假判断不同：“口播简短”适合持久化，“库存180”可能立刻过期，“已发20张券”需要提交证据。混成摘要容易让旧数字和模型推断获得不该有的可信度。

当前偏好不是多条结构化用户画像，没有自动去重、TTL或跨直播场次画像体系。它按 `live_id` 保存，重启后能读；不是已实现的主播账号级长期记忆。讨论状态按 `live_id + scene` 管理，也没有完整多人私聊隔离。

若声明“优先讲SK-101”，最近三次已提交切品却全是其他SKU，窄规则可以带事件ID提示差异，询问用户而不覆盖声明。若声明是“开场先讲101”，普通后续切品不能证明违反开场要求，证据不足时返回待判断。

**记忆、上下文、Checkpoint 的区别**：记忆是可复用信息；上下文是本次实际递给模型的材料；Checkpoint 是暂停任务的进度。持久化不等于每次全部塞入提示词。

### 9. 持久化用什么？为什么不直接上 Redis 和向量库？

**主答：当前以SQLite保存可审计状态，LangGraph另用SQLite Checkpoint保存审批进度；结构化、按ID查询的数据暂时无需向量检索。**

| 数据 | 存储位置 |
|---|---|
| 商品、直播状态、券、命令、幂等账本、审计、偏好 | 业务SQLite |
| 阶段事件、话题投影、对话记录、完整回答 | 同业务库的 `runtime_*` 表 |
| DAG状态、租约、材料、计划历史 | `campaign_runs / campaign_artifacts` |
| 模型额度、请求预留与usage | `provider_scopes / provider_calls` |
| 人工审批暂停与恢复 | 独立LangGraph SQLite Checkpoint库 |
| 发券远端协议仿真 | 独立平台SQLite，模拟本地与远端两个账本 |

业务SQLite启用WAL，连接等待上限10秒。写操作使用事务；状态、版本、唯一键和账本一起约束结果。WAL改善读写共存，**不让SQLite变成多个写者同时提交的分布式数据库**。

Redis适合后续缓存、限流或短期协调，但不能仅靠缓存判断券是否真的发出。向量库适合大量非结构化历史语义召回，不适合代替明确SKU、库存或命令身份查询。

生产扩展方案是：业务状态、唯一约束和审计迁移到PostgreSQL，Checkpoint采用相应持久化后端；Redis用于限流等辅助状态，长材料量大再外置对象存储。迁移前需验证事务与恢复语义，而非换数据库名就算完成高并发。

### 10. 高并发怎么处理？现在到底验证到了哪里？

**主答：当前解决了本机请求互斥粒度、商品任务并行和数据库冲突，尚未证明多租户、大流量真实模型服务容量。**

同一 `command_id` 在单进程内共用一把锁，防止同指令同时推进；不同命令可以并行。业务提交依靠数据库事务、唯一键、版本和幂等账本，不能把进程内锁当成跨机器锁。

同一准备计划使用60秒数据库租约；保存时再次检查owner与有效期，失去租约的执行器不能覆盖结果。子任务默认3线程；这只是计划内部并发，多个计划叠加后的全局并发仍需额外治理。

已存档的本机基线是在2026-10-19生成的，虽然文件名含20261017。1/4/8 worker各3轮、每轮100请求：各自300/300完成；各轮吞吐中位数约212/325/316请求每秒，对应各轮P95的中位数约5.28/18.33/34.88ms。

它是**单进程内直接调用离线Agent**，不经过HTTP网络、不调用模型，worker内计时还不含线程池排队；不能写成线上QPS或真实API端到端P95。8线程没有继续提升，提示增加并发存在争用或饱和，但未做剖析，不能直接认定唯一瓶颈是SQLite。

下一步先补入口队列、全局/租户模型并发限制、RPM/TPM限流和背压；长任务放队列，接口返回任务ID。再在真实API与数据库配置下做含排队的负载测试，分开测接入延迟、模型等待、生成耗时和审批等待。当前累计调用预算也不等于速率限制。

### 11. 调了什么工具？是不是 native Function Calling？

**主答：主播项目当前主要是JSON动作解析，再由Python固定分发；没有使用供应商原生 `tools/tool_calls` 循环。**

主链能查询状态、推荐、生成口播、复盘、创建准备计划、记录偏好，以及受控切品/改价/发券。准备链只开放角色技能 `catalog、product、review、assemble`。模型HTTP请求与本地工具执行不是同一计数。

例如一次“推荐三款”可能先请求模型理解，再请求模型组织建议，本地还会读取商品和校验排序。不能把它说成“总共两次工具调用”。

如果面试官问为什么不用原生Function Calling：当前每条指令只接受一个受限动作，明确JSON契约已足够；原生协议可以改进工具交互标准化，但不会自动替代参数来源校验、审批、事务幂等和unknown对账。论文Agent的native实现是另一项目能力，不能借到这里。

### 12. 失败如何处理？为什么不能统一重试？

**主答：按“临时服务错误、输入或契约错误、事实变化、执行结果未知”分别处理。**

| 具体例子 | 当前处理 / 原因 |
|---|---|
| 意图接口超时、429、5xx | 最多两次模型尝试，失败可降级规则；降级来源留审计 |
| 意图返回坏JSON | 剩余尝试内要求修正一次；不是无限反思 |
| 模型返回401或参数类4xx | 不按临时错误盲目重试，记录服务错误；意图路径可离线降级 |
| 写手暂时性失败 | 内部请求有限尝试；任务仍失败时保存断点，允许受控恢复 |
| 缺数量、未知SKU、无权限 | 补输入或停止，不能重复相同请求碰运气 |
| 商品/偏好变化 | 读新事实，明确重规划或重新确认 |
| 发券已发送但没收到响应 | 标unknown，查询原身份回执；连续三次查询仍未确认转人工处理 |
| 模型额度耗尽 | 停止新模型调用；能用确定性结果的路径可降级，准备任务保留状态 |

两层“2次”要讲清：一次写手任务内部最多2次模型请求，任务执行本身默认最多2次尝试，因此跨恢复可能多于2次HTTP请求。它们都受共享模型预算限制，不能简单说“整个任务永远只花2次调用”。

发券unknown尤其不能重试写入：服务端可能已经成功，重发会重复发券。本地outbox保存身份与动作hash，回执必须匹配操作ID、SKU、金额、张数后才能记账；当前是显式查询的仿真协议，不是完整生产消息平台。

### 13. 成本和响应时间怎么控制？上限是多少？

**主答：减少不必要上下文、重叠独立等待、复用有效材料，并在请求前持久化预留预算。预算包括失败、修复和恢复期间的调用。**

| 约束 | 当前默认值 / 含义 |
|---|---|
| 单指令模型准入 | 6次请求、100000预估token |
| 单准备计划 | 最多20次请求、300000预估token；创建时可降低 |
| 同一直播间累计 | 200次请求、2000000预估token，不自动补充 |
| 计划总执行 | 默认24个任务执行；重规划不清零 |
| 单次推进 | 30秒，在波次边界检查；不强行终止在途请求 |
| 单任务恢复 | 默认最多2次任务尝试；同计划最多2次重规划 |
| 模型请求超时 | 意图8秒、建议15秒、写手5秒，都是各自请求配置 |
| 人工审批 | 默认300秒有效；到期需要重新发起 |

请求前先在SQLite事务里预留调用与估算token；返回合法usage后对账，网络错误、usage缺失或进程中断保留预留。估算依据消息UTF-8字节数、输出上限与固定开销，**不是供应商精确分词，也不是金额硬封顶**。同一command/run恢复和重启不刷新额度。

线程池worker不会自动继承调用线程的 `ContextVar`；代码在每个模型写手worker中显式绑定相同计划scope，避免多角色绕过额度。

这些是当前演示默认值，没有实验证明最优。尤其直播间累计200次不自动补充，长直播可能耗尽；生产应区分租户/日期/场次额度、消耗告警与授权补额，同时做速率限制和价格版本账本。30秒推进边界也不是整条请求严格30秒返回的保证。

响应时间看阶段：备播可以容忍批量生成，播中应尽量走清晰查询或少轮建议，交易还必须拆出人工等待。现有对话开发记录10条指令响应中位数2.218秒，只是小样本，不能当线上SLO。

### 14. 为什么评估这些指标？不同方法真的对比过吗？

**主答：指标分别对应“听错、编错、等太久、重复花费、恢复错误、业务越权”六类风险；确实做过组件级对照，但没有完整证明多Agent优于单Agent。**

先讲为什么测，再报结果：

| 业务风险 | 指标及计算口径 | 为什么需要 / 还缺什么 |
|---|---|---|
| 听错动作或商品 | 联合匹配率＝动作、SKU、关键金额/数量均符合标注的题数÷全部题数 | 只看动作类型会漏掉“发对动作、发错商品”。另应独立测该澄清是否澄清、把讨论误当执行的比例 |
| 材料含错数字或来源 | 字段审核通过率；错误稿误放率＝放行错误稿÷错误稿数；正常稿误拒率＝拒绝正常稿÷正常稿数 | 只追求拦截率会把全部材料都拒绝；需同时看有效覆盖与人工修改 |
| 主播等待过久 | 同任务端到端耗时中位数、P95，分离排队、模型与人工审批 | 均值会掩盖尾延迟；已有小样本不够支撑生产P95 |
| 修复造成重复消耗 | 全部请求数、已知usage、未知usage次数、任务尝试、成功分支重跑数 | 失败也会花费；字符减少不能直接当费用减少 |
| 长对话丢对象 | 指代目标正确率、歧义澄清率、跨阶段串扰、旧事实误用 | 目前只有机制测试及一个真实模型长间隔指代场景，没有总体准确率 |
| 状态或权限错误 | 未授权写入、重复提交、旧审批失效、unknown对账等场景检查 | 任务完成不代表安全；正确拒绝也是合格结果 |
| 建议没有实际用处 | 采纳率、修改率、评分、人工修改量 | 当前有反馈存储；没有真实运营收益或因果提升结果 |

实际做过的对照如下，实验条件与结论必须一起说：

| 要验证的选择 | 对照方式与结果 | 能说明什么 / 不能说明什么 |
|---|---|---|
| 模型解析是否值得 | 同24条开发题、同快照：规则19/24，真实模型20/24；普通16/16 vs 14/16，挑战3/8 vs 6/8 | 模型更能覆盖部分挑战表达，也有退化；不是独立测试集，不能证明普遍胜出 |
| 独立商品是否应并行 | 相同DAG、真实写手，1/3 worker各5次：中位2.995→1.070秒，两组各15张手卡通过字段核验 | 支持重叠网络等待；不是单/多Agent回答质量对照 |
| 是否该按角色裁上下文 | 1–5商品共40个任务包，全量共享238069字符，裁剪26415字符，少88.904% | 本地包体更小，成本字段未进入这40个包；没有实测节省同比例token或费用 |
| 恢复时是否全量重跑 | 本地注入临时失败，各10次：全量140次任务尝试，局部90次，少35.714% | 减少已成功分支的重做；无模型调用，不能换算真实费用 |
| 商品变化是否增量replan | 一个真实写手开发场景：恢复模型请求3→1，任务8→4，复用4个任务，耗时1.166→1.140秒 | 减少重复调用；两组各一次，耗时接近，不证明显著提速 |
| 字段审核是否必要 | 45个预设错误稿：关审核放行45，开审核放行0；5个正常稿均通过 | 说明这组契约错误可拦截；不是自然模型幻觉率为零 |
| 并发数是否越大越好 | 本机离线直接调用，1/4/8 worker吞吐中位数212/325/316次每秒 | 在该负载下8线程无继续收益；不是HTTP或真实模型容量 |

**没有做过的关键对照**：单Agent+Skills vs 多角色DAG的自然语言质量；规则/结构化/向量记忆的长期收益；不同模型、不同完整架构在相同费用预算下的质量比较。不能把“调度并行更快”讲成这些结论。

如果继续评测，固定商品快照、模型、工具、任务和总预算，使用新的未参与修改的题目；比较单Agent+Skills、共享上下文多角色、局部上下文多角色，按任务配对，同时报告成功、误拒、安全、全部调用和延迟。语气、创意与业务价值需要人工盲评；只让一个模型给另一个模型打分不足以证明质量。

当前面板还有两处口径要讲清：`ok_rate` 是ok÷终态命令数，分母含澄清/拒绝，不能叫业务准确率；`acceptance_rate` 是每条建议的最新显式反馈中采纳的比例，未反馈的建议不在分母，不能叫全体主播采纳率。无反馈时返回空值。GMV与因果提升未测。

### 15. 讲一个真实难点，如何讲出工程经验？

**主答：讲“具体触发条件→错误机制→改法→验证→代价”，不要只背用了哪个框架。下面是本地开发问题，不是线上事故。**

**意图难点：模型自己补出一张券。** 旧开发实验里，“给面霜发10元券”被补成quantity=1，条件句也曾变成立即执行候选。问题在于合法参数不代表来自用户。当前入口增加原指令检查、缺参澄清、条件语句只讨论，并补回归。10条新版开发对话中的9项流程检查通过，但不是修复前后同一独立测试集，不声称准确率从83.3%升到100%。

**上下文难点：推荐文本被裁掉，第二款还要指对。** 如果只保留最近聊天，早期顺序会丢失；如果全留，输入持续增长。我把接纳的推荐顺序和焦点变成分阶段状态，原文完整外置。用8轮离线插话后的真实模型追问验证了目标绑定。代价是需要维护明确状态字段，尚不能覆盖所有自由语义。

**状态难点：切回播中，旧审批不应该复活。** 只检查当前scene会漏掉“播中→播后→播中”期间的变化。现在 `revision` 记录所有上下文事件，`control_revision` 只在阶段改变时递增；提案绑定后者，提交前再验。在线人数变化不增加控制版本，避免普通观测误伤审批。存档回归覆盖本地与远端派发两条路径；已发送的远端请求仍需对账，不能靠切阶段撤回。

选一个自己最熟悉的故事讲深即可。若被问遗留缺陷：当前主要欠缺多租户鉴权、真实平台接口、完整语义审核、全局并发限流和生产容量验证；下一步按业务风险排序补，不先堆更多Agent。
